# v2-2026-10-09 多套订阅配置

## 目的

现在同一服务可以管理多套彼此独立的订阅配置。此前所有设置、脚本和缓存共用一个全局状态，无法在同一实例内为多个 Surge 客户端提供互相独立的托管配置。

## 主要改动

### 多配置模型

- 每套配置独立保存：上游链接、请求头、对外访问地址、更新间隔、脚本、缓存与拉取状态（最后一次错误、尝试时间、成功时间）。
- 多套配置可同时被不同的 Surge 客户端订阅，互不影响。
- 订阅路径为 `/subscription/<id>`，链接前缀由该配置的对外访问地址决定，留空时使用当前请求地址。
- 用户自定义 `id` 必须匹配 `^[a-z][a-z_-]{0,15}$`（小写字母开头，仅含小写字母、下划线和连字符，长度 1–16），创建后固定不改；重命名只改名称，不影响订阅链接。`name` 仅用于展示，必填且允许重名。

### 管理操作

- 支持新建、复制、重命名、删除。复制会深拷贝设置与全部脚本（脚本为独立副本），不复制缓存和拉取历史。
- `default` 在页面和 API 中都禁止删除。
- 管理页切换配置时只切换编辑对象；存在未保存的设置或脚本修改时先提示确认，可以取消。切换期间表单清空并禁用，未加载完成的配置不会被写入；重命名不重置正在编辑的草稿。

### 兼容与迁移

- 旧单实例 `state.json` 在首次启动时自动迁移为一套配置：`id=default`、名称为“默认配置”，保留全部设置、脚本、缓存和拉取历史，并持久化为 `{ "version": 2, "profiles": { ... } }` 结构；迁移幂等，全新部署也自带 `default`。
- 旧入口 `/subscription` 与旧单实例 API 路径仍然可用，固定对应 `default`；服务端没有全局“当前配置”，所有 API 绑定到具体配置（`/api/profiles/<id>/...`）。

### 并发与过期请求

- 刷新接口和订阅入口在拉取期间若配置被修改，本次结果作废并返回 409（要求重试）；配置被删除或重建则返回 404。避免返回“旧上游 + 新脚本”的混合配置。
- 各配置的“立即拉取并转换”互相独立，可以同时进行。
