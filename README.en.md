# Surge Subscription Proxy

A small service you host yourself: put your subscription URL into a web page, it adds your own rules on top, and gives Surge an address it can subscribe to.

## What this service does

Most Surge users have an **upstream subscription URL** (from a provider). Surge subscribes to it and gets nodes and rules.

That works, but it gets annoying quickly:

- Whenever the upstream is updated, the rules and groups you added yourself are gone;
- To change rules you have to edit the profile inside Surge, and repeat that on every device.

This service sits in between and passes things along:

```
upstream subscription URL ──► this service (fetch → append text → run scripts → output) ──► Surge subscribes to this address
```

Every time Surge refreshes the subscription, the service fetches the latest upstream profile, adds the rules you configured, runs your scripts, and hands the complete result back to Surge. You change things once on the web page, and every device subscribed to that address picks it up.

**In short: the upstream owns the nodes, you own the rules.**

## Requirements

- A machine: NAS, mini PC, Raspberry Pi, or a cloud server. You can also just use the same computer where Surge is installed — no need for a separate machine (it does not have to run all the time, see "Only for Surge on the same machine? Start it when you need it");
- Docker (recommended) or Node.js 22+ on that machine;
- An upstream subscription URL that returns a **complete Surge profile**;
- If you want to use it from outside your network, prepare a VPN or a tunnel first (see "Security notes").

## Quick start (Docker, recommended)

### 1. Get the code

```sh
git clone <this repository> surge-subscription-service
cd surge-subscription-service
```

### 2. Start it

```sh
docker compose up -d --build
```

### 3. Open the admin page

From a browser on the same network:

```
http://<machine-ip>:3080/
```

For example `http://192.168.1.10:3080/`.

### 4. Enter your upstream URL

Paste your upstream subscription URL into "Upstream settings" and click "Save settings".

Not sure what headers to use? **Leave them alone.** The service sends `User-Agent: Surge` by default, which most upstreams accept. Add headers only if your upstream requires them.

### 5. Fetch once to try it

Click "Fetch and transform now". On success the page shows a timestamp; click "View last successful config" to see the final result.

### 6. Get the subscription link

The address shown under "Surge subscription link" is what Surge should subscribe to. Click "Copy link", or click "Import to Surge" if Surge is installed on this machine.

### 7. Import it in Surge

Surge → Profiles → download a profile from URL, then paste the link. Surge will refresh it automatically at the configured interval.

To change rules later, come back to this web page.

### Common commands

```sh
docker compose logs -f        # view logs (useful when troubleshooting)
docker compose restart        # restart
docker compose down           # stop and remove the container (data lives in a named volume, it is kept)
docker compose up -d --build  # rebuild after updating the code
```

If a reverse proxy (Nginx, Caddy, ...) is already running on this machine, you can bind to localhost only:

```sh
HOST_BIND=127.0.0.1 docker compose up -d --build
```

## Run without Docker

Requires Node.js 22 or newer. The project has no third-party dependencies, so there is **no** `npm install` step.

```sh
npm start
```

It listens on port 3080; open `http://127.0.0.1:3080` in your browser.

To change the port or the data directory:

```sh
PORT=3081 DATA_DIR=./data node src/server.js
```

## Only for Surge on the same machine? Start it when you need it

You do not need a machine that runs 24/7. The service can live on the same computer as Surge, and you only **start it when you need it, then stop it**:

1. Run `npm start` in the project directory (Node.js 22+ required);
2. Open `http://127.0.0.1:3080`, fill in the upstream URL and your rules;
3. Import the subscription link shown on the page into Surge, and update the profile once;
4. Once Surge is using the new profile, press `Ctrl-C` in the terminal to stop the service.

**Stopping it does not break anything.** Surge keeps using the profile it last downloaded. The managed link generated by this service does not include the `strict` parameter, and according to the [Surge documentation](https://manual.nssurge.com/profile/managed-profile.html) a failed update then simply means you keep using the previous profile — no harm done, the update just did not happen.

When you want to change rules again, run `npm start` once more and refresh the profile in Surge manually. If you would rather Surge did not keep trying to update while the service is off, set a longer update interval (up to 604800 seconds, i.e. 7 days) and update manually when needed.

Two things to keep in mind:

- The address inside the subscription link must be reachable **from wherever Surge runs**. For Surge on the same machine, `127.0.0.1` is fine. If a phone on the same network should subscribe too, set "Public base URL" to this machine's LAN address (for example `http://192.168.1.10:3080`), and the service must be running while the phone updates.
- Docker works this way too: start it with `HOST_BIND=127.0.0.1` and stop it with `docker compose stop`.

## What you can do on the web page

The page has five blocks, in the order you would normally use them.

### Profiles

One complete set of settings is called a Profile. You can create several — "phone", "laptop", "family" — each with its own rules and its own subscription link, independent of each other.

- **New / Copy / Rename / Delete**: copying duplicates settings and scripts (the cache is not copied);
- **Import / Export**: export a JSON backup to move a profile to another machine, or import one under a new ID;
- The profile named `default` cannot be deleted; it exists for backward compatibility;
- An ID must start with a lowercase letter, may contain lowercase letters, digits, underscores and hyphens, and is at most 16 characters. It cannot be changed after creation, because it is part of the subscription link.

### Upstream settings

Tells the service where to get the original profile.

| Field | Meaning |
| --- | --- |
| Upstream Surge profile URL | Your upstream subscription address. Required. |
| Public base URL | Optional. When empty, the subscription link is built from the address you are currently using to open the page. Behind a reverse proxy or HTTPS, fill in the full address (for example `https://surge.example.com`) so the generated link is correct. |
| Managed profile update interval | How often Surge refreshes, in seconds, 60–604800 (default 86400, i.e. 24 hours). |
| Upstream headers | HTTP headers sent when fetching the upstream. By default only `User-Agent: Surge`. You can add, edit or remove them. |

### Text appends (use this if you do not write code)

This adds lines of config to a section — no JavaScript required.

Example: to send `example.com` through DIRECT, add the line `DOMAIN-SUFFIX,example.com,DIRECT` at the top of the `Rule` section.

Each append item has:

- **Name**: anything you like, just to recognise it;
- **Section name**: where to add the text, e.g. `Rule`, `Proxy Group`, `General`;
- **Position**: first or last;
- **Create section if missing**: when checked, the section is created if the upstream does not have it;
- **Overwrite whole section**: when checked, the text replaces the entire section instead of being inserted;
- **Enabled**: toggle it on and off without deleting it.

Multiple items run in list order, and **text appends run before scripts**.

### Transform scripts (use this if you write JavaScript)

When appends are not enough, write JavaScript to modify the profile:

```js
module.exports = (config) => {
  config.rules = [
    'DOMAIN,registry.hub.docker.com,节点选择',
    ...(config.rules || []),
  ];
  return config;
};
```

- Enabled scripts run from top to bottom; each one receives the result of the previous one;
- Sections are accessible by name, e.g. `config['General']`, `config['Proxy Group']`; `config.rules` is a shortcut for `[Rule]`;
- The editor has line numbers, search and word wrap. Clicking "Check" only validates the syntax — it does not save or run anything;
- A tutorial with more examples is in [`docs/script-guide.md`](docs/script-guide.md) (Chinese); the same guide is built into the web page ("View script guide" at the top).

### Subscription link and status

- **Copy link / Import to Surge**: copy the subscription address of the current profile, or open it in Surge directly via `surge:///`;
- **Fetch and transform now**: fetch the upstream immediately, handy for testing whether your rules work;
- **View last successful config**: see the exact output — you can search it to check whether your rule made it in;
- On failure the page shows the actual error (upstream unreachable, script error with line number, ...).

## Troubleshooting

| Symptom | Where to look |
| --- | --- |
| The page does not open | Is the container running (`docker compose ps`)? Is the IP and port correct? Is the firewall allowing it? |
| Surge shows an old profile | Click "Fetch and transform now" and read the error; check that the upstream URL opens in a browser |
| My rules are not applied | Click "View last successful config" and search for your rule; rule order matters — do not place it after `FINAL` |
| A script fails | The page names the script and the line; use the "Check" button to validate it on its own |
| The upstream cannot be fetched | The upstream may require specific headers — add them under "Upstream headers"; it may also be blocking your IP |
| I want another port | Change the port mapping in `compose.yaml`, or set `PORT` when running locally |

**A failed fetch never returns an empty profile.** If the upstream is unreachable, the service keeps serving the last successful result, marked as stale, and shows the error on the admin page. So your config will not suddenly break.

## Security notes

- **The admin page has no login.** Anyone who can open the address can see your upstream URL and change your rules. Do **not** expose it directly to the internet: keep it on your local network, or reach it through a VPN or tunnel. If you put a reverse proxy in front, add access control yourself.
- The data file stores your **upstream URL and scripts in plain text**. Look at it before backing it up, sharing it or uploading it anywhere.
- Exported JSON backups contain the same sensitive information (upstream URL, headers, scripts).
- Transform scripts are **code you wrote yourself** and the service executes them directly. Do not paste scripts from unknown sources — the sandbox is not a security boundary.

## Advanced

### Environment variables

| Variable | Default | Purpose |
| --- | --- | --- |
| `PORT` | `3080` | Port the service listens on |
| `DATA_DIR` | `./data` (local runs) | Where data is stored; inside the Docker image this is `/data` |
| `HOST_BIND` | `0.0.0.0` | Used by `compose.yaml` only: which host address the port is bound to. `127.0.0.1` allows local access only. |
| `NODE_ENV` | — | Set to `production` in the Docker image; you normally do not need to touch it |

### Where the data lives

- Local runs: `./data/state.json`;
- Docker: `/data` inside the container, backed by the volume named `surge-data` in the compose file.

That file holds every profile's settings, scripts, cache and last error. Deleting it is a factory reset; backing it up backs up everything.

### Subscription link rules

- Each profile is served at `/subscription/<profile-id>`, for example `/subscription/phone`;
- The old path `/subscription` always points to the `default` profile, so existing links keep working;
- The prefix comes from "Public base URL"; when empty it is derived from the current request;
- Every request fetches the upstream again and re-runs the transformation; there is no background refresh.

### What happens on a single request

1. Surge requests the subscription link;
2. The service fetches the latest upstream profile (15 second timeout, 15 MB size limit);
3. It parses the profile into sections (`[General]`, `[Rule]`, ...). Sections you did not modify are kept byte-for-byte, including comments and blank lines;
4. It applies your enabled text appends in order;
5. It runs your enabled scripts in order (each script is limited to 500 ms and must be synchronous);
6. It prepends a `#!MANAGED-CONFIG` line pointing back to this service and returns the result to Surge.

If the fetch or the transformation fails: the last successful result is returned instead (the response carries `X-Subscription-Stale: true`), or an error is returned when there is no cached result. If the profile is modified while a fetch is in flight, that fetch is discarded so you never get an "old upstream with new scripts" mix.

### Main API endpoints

Everything the web page does is also available over HTTP.

| Method | Path | Purpose |
| --- | --- | --- |
| GET / POST | `/api/profiles` | List / create profiles |
| GET / PUT / DELETE | `/api/profiles/<id>` | Read / rename / delete a profile |
| POST | `/api/profiles/import` | Import a JSON backup |
| GET | `/api/profiles/<id>/export` | Export a JSON backup |
| GET / PUT | `/api/profiles/<id>/state`, `/settings` | Read state / save upstream settings |
| GET / POST | `/api/profiles/<id>/preview`, `/refresh` | View last successful config / fetch now |
| POST | `/api/profiles/<id>/scripts`, `/scripts/validate` | Create a script / validate syntax only |
| PUT / DELETE | `/api/profiles/<id>/scripts/<script-id>` | Update / delete a script |
| POST | `/api/profiles/<id>/scripts/<script-id>/move` | Reorder scripts |
| POST | `/api/profiles/<id>/appends` | Create a text append item (`/appends/<id>`, `/move` work the same way) |

The old single-profile paths (`/api/state`, `/api/settings`, `/api/preview`, `/api/refresh`, `/api/scripts`) still work and always operate on the `default` profile.

### Limits

| Item | Limit |
| --- | --- |
| Upstream profile size | 15 MB |
| Upstream fetch timeout | 15 seconds |
| Single script run time | 500 ms |
| Script code length | 100,000 characters |
| Script / append name | 100 characters |
| Append text length | 100,000 characters |
| Update interval | 60–604800 seconds |
| Request body size | 1 MB |

## Development and testing

```sh
npm start   # run locally
npm test    # run the tests (Node's built-in test runner, no dependencies)
```

The project only uses Node.js built-in modules, there is no build step — restart the process after changing the code.

### Project layout

```
src/server.js        HTTP server, admin API, upstream fetching, persistence
src/profile.js       Surge profile parsing, script execution, serialization
public/              Admin page and script guide (shipped in the image)
test/                Automated tests
data/                Data directory for local runs (git-ignored)
compose.yaml         Docker Compose entry point
Dockerfile           Image build
```
