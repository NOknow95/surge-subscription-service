# 写 changes 变更说明

> `changes/` 是给用户和开发者看的**变更记录**，不是工作日志、不是部署记录、不是验收报告。

## 什么时候写

写：功能改动、用户可见行为变化、接口/配置/存储格式变化。

不写（跳过）：
- 只改 `AGENTS.md` 规则本身
- 只改 skill、工具链、CI、配置、流程文档
- 纯格式、纯重命名、纯注释

**收尾前必须问用户"这组改动是否完成"**，用户确认完成后才写。

## 先跑这个脚本，别手算版本号

```sh
./.agents/skills/write-changes/scripts/next-version.sh
```

它输出：今天的日期（**Asia/Shanghai**）、现有最高版本号、下一个版本号、建议文件名，以及**当天是否已有变更说明**。

结果决定下一步：

| 脚本输出 | 动作 |
|---|---|
| 当天没有变更说明 | 直接新建 `changes/v<N>-<今天>.md`，无需询问 |
| 当天已有变更说明（一份或多份） | **停下来问用户**：合并进已有文档，还是新建版本文档。多份时还要确认合并的目标是哪一份 |

不得自行决定新建还是合并。

## 三条硬规则

1. **版本号全局连续，不按天重置**：取 `changes/` 里所有文件名的最大值 + 1（如已有 v9，即使当天还没文档，新文件也是 v10）。已有版本号绝不覆盖、绝不复用。
2. **同一组改动沿用同一次选择**：围绕同一目标的需求、补充、修正、验收反馈都算一组。组内一旦确定过"合并到某文档"或"新建某文档"，后续改动沿用，不重复问；用户明确结束该目标或主动改选时才重新判断。
3. **日期用 Asia/Shanghai**：`TZ=Asia/Shanghai date +%F`。本机时区可能不是东八区，跨零点写错日期等于写错文件名。

## 文档结构

骨架见 `assets/template.md`，照它写：

```markdown
# v10-2026-11-01 一句话说清这次改了什么

## 目的
为什么改：遇到的问题、旧行为为什么不行。

## 主要改动
- 行为/接口/配置逐条列，带上具体的字段名、命令、文案变化。

## 迁移影响
有破坏性变更、需要用户手动操作时才写；没有就整节省略。

## 验证
自动化结果：`npm test` 通过项数、新增的断言、`node --check`。
```

标题第二段是**主题**，不是任务号、不是人名、不是版本说明。

## 该写 / 不该写

写：
- 改了什么行为、新增或修改了哪些接口字段与配置项、默认值变化
- 修了什么问题（可以描述现象，如"拉取失败只看得到 `fetch failed`"）
- 破坏性变更与迁移步骤
- 可复现的自动化验证结果（`npm test`、`node --check`、新增用例断言了什么）

不写：
- **部署过程**：在哪台机器构建、`docker compose up -d`、镜像 tag、容器名、重启了几次
- **环境标识**：主机名、内网/Tailscale IP、NAS 路径、代理地址、真实的 profile 名、真实上游域名
- **验收叙述**："已部署成功""容器正常运行""某 profile 现在正常了""订阅链接返回 200"
- 讨论过程、"应某要求""按用户反馈"这类过程信息
- 手动点点看的结论；要写就写能用命令复现的

需要举例时用占位符：`<host>`、`<port>`、`example.com`、`192.0.2.10`（TEST-NET-1）、`host.docker.internal`。

## 收尾流程

1. 跑 `scripts/next-version.sh`，按结果决定新建或询问用户
2. 写/改文档
3. 提交前自查（本地若装了提交前敏感信息审查 skill，例如 `precommit-sensitive-review`，直接跑它的脚本；没装就按下面清单手工过一遍）：
   - 有没有主机名、内网 IP、绝对路径、真实域名、真实 profile 名、镜像 tag
   - 有没有部署/验收叙述（"已部署""容器正常运行""某配置现在正常了"）
   - 有没有贴真实订阅链接、请求头、脚本内容
   - `git diff --check` 没有行尾空格
4. 提交前再问一次用户这组改动是否真的结束（未结束就继续，别急着记录）

## Gotchas

- **版本号不是每天从 v1 开始**：同一天可以有 v8、v9 两个文档，也可能出现跨天连续编号。
- **老文档里的写法不要照抄**：早期文档有"已并入初始提交，尚未部署"这类句子，属于旧习惯，新文档不写部署状态。
- **验证只写自动化可复现的部分**：`node --check`、`npm test` 的通过项数与新增断言。手工验证如果要写，必须写成别人能照着跑的命令和期望输出，不写"我点了下按钮，好了"。
- **写完后 `git diff --check`**，避免行尾空格和 tab 混排。
- **本地可能装有 `precommit-sensitive-review` skill**（不进本仓库）：它能自动扫描上面这些环境标识与凭证；没有它时手工检查，不要跳过这一步。
- **文档里不要贴真实订阅链接、请求头、脚本内容**：这些属于运行数据，仓库是公开的。
- **改动涉及脚本接口时**：按 `AGENTS.md`，除了 changes 还要同步 `public/script-guide.html`、`docs/script-guide.md` 和管理页提示，changes 里要把这些一并列出。
